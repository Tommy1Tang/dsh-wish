# 例子：两份契约，一份合格一份不合格

这两个文件**不是示意，是真的会被 `contract_lint.py` 判定的**。
每次提交 CI 都会跑一遍（`tests/test_examples.py`），所以它们不会随着规则改动而变味。

```bash
python contract_lint.py examples/contract-good.md   # PASS
python contract_lint.py examples/contract-bad.md    # FAIL（9 条 error）
```

---

## contract-good.md —— 合格

一个真实场景：把齐套报表的齐套率从「按数量」改成「按金额」。

它演示了合格契约该有的全部要素：

| 要素 | 在哪 |
| --- | --- |
| AC 有可观测对象（文件名、数字、字段名、界面元素） | AC-01 ~ AC-05 |
| 每条 AC 都有**反例**（"能通过但我不满意"的场景） | 每条 `> 反例：` |
| 状态/异常类用 **EARS 句式**（When / While / If） | AC-02、AC-03、AC-04、AC-05 |
| 「本次不做」明确写了 | 第 2 节末 |
| **状态枚举**与 AC 一一对应 | 3 个状态 → AC-03/04/05 各覆盖一个 |
| **放弃条款**给理由码 + 签字人 | 第 6 节 |

> 写这份例子时，我自己漏了「已加载」和「加载失败」两个状态，被 E8 拦下来了。
> **这正是 E8 的用处**：漏状态不会让任何测试变红，只会让需求缺一块。

---

## contract-bad.md —— 不合格

一份"两分钟写完"的契约，把新人最常犯的错都犯了一遍：

| 行 | 犯了什么 | 触发 |
| --- | --- | --- |
| `AC-01` 没有 `> 反例：` | 举不出反例 = 没钉住 | **E1** |
| `AC-03` 只有一句话，没有「判定方式」 | 无法验收 | **E2** |
| 「导出功能要**好用**」「加载速度要**快**」 | 主观词，一人一个理解 | **E3**（快 → W2 软提示） |
| 「数据要准确」「及时通知」 | 偏主观但常与数字并存 | **W2**（只警告） |
| 三条 AC 都没有任何可观测对象 | 无法机械判定 | **E4** |
| 没有「什么情况下可以放弃」整节 | "这活不用做"只能伪装成完成或卡住 | **E5** |
| 「订单状态变化时……失败的话要重试」 | 状态/异常却没用 EARS 句式 | **E7** |
| 声明了 3 个状态，一条 AC 都没覆盖 | 漏场景 | **E8** |
| 「本次不做」是 `{{OUT_OF_SCOPE}}` 占位符 | 范围没边界 | **S1** |
| AC 编号 `01 → 03 → 04` | 跳号说明有 AC 被删过 | **S2** |

**这些不是"风格问题"，每一条都对应一次真实的返工。**

---

## 怎么用这两份例子

- **给人看**：新人第一次写契约，先读 `contract-good.md`，再看 `contract-bad.md` 差在哪
- **给校验用**：改 `contract_lint.py` 的规则后，跑 `python run_tests.py`——
  如果好例子突然 FAIL 或坏例子突然 PASS，说明规则改坏了
- **当模板改**：`templates/contract.template.md` 是空壳，`examples/contract-good.md` 是填好的样子
