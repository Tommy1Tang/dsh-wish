## 2. 验收条目

**每条 AC 必须只有一种读法。** 判定标准：两种读法都能通过 → 不合格，重写。

写法要求（`lint_contract` 会机械检查前三条）：

- [ ] 含**可观测对象**：页面元素 / 字段名 / 文件名 / 数值比较（不许只有动词）
- [ ] 含**反例**：举一个"它能通过但我仍不满意"的场景
- [ ] 无**模糊词**：友好 / 合理 / 尽量 / 快速 / 适当 / 较好 / 完善 / 优化一下
- [ ] **涉及状态/异常的，用 EARS 句式开头**（`When` / `While` / `If` / `Where`，或 `当` / `在` / `如果`）

> EARS 句式不是为了让文档好看，是为了**把读法压到一种**：
> 「订单状态变化时通知用户」有三种读法（变化前后？通知谁？失败怎么办？）；
> 「**When** 订单从待支付变为已支付，系统向下单人推送 1 条通知，失败重试 3 次」只有一种。

## 8. 什么情况下可以放弃（dropped）

> **放弃不是「跳过」，是「确认不做」。** 没有这一节，执行者只能用
> 「完成」（假装做完）或「卡住」（触发返工）来表达「这活不该做」，两种都在污染证据链。

| 理由码 | 含义 | 确认人 |
| --- | --- | --- |
| `not-reproducible` | 复现不出来（查了 N 次没有） | 提需求的人 |
| `obsolete` | 需求已过时 / 被废弃 | 业务方 |
| `already-exists` | 现有功能已覆盖 | 提需求的人 |
| `out-of-scope` | 不属本项目范围 | 项目负责人 |

**规则**：报 dropped 必须同时给理由码和确认人；缺一按 `blocked` 处理。
理由码不许自己编——编出来的理由等于没有理由。
